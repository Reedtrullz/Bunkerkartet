# Browser workflows: selected exchanges, pilots, and local notebook

The additive browser module `app/static/workflow-ui.js` mounts bounded workflow sections when the authenticated page emits `bunkerkartet:detail`. The application shell includes the module once; its browser tests wait for that native script load rather than injecting a second copy. The standalone `app/static/offline-notebook.html` is an empty shell and loads only its local notebook module. Neither file contains a private package by default.

## Workflow boundaries

| Workflow | Explicit browser action | Server boundary | Data omitted by default |
|---|---|---|---|
| Selected dossier (BK24) | Select dossier options, preview, then request a download bound to the same preview hash | `/api/admin/exchanges/dossiers/preview` and `/download` | Private start, questions, and observations |
| Import subset (BK45) | Read a bounded JSON file with the app's strict parser, select stable keys, assign a new batch ID, preview, separately confirm, and commit the previewed hashes | `/api/admin/exchanges/import-subsets/preview` and `/commit` | Unselected source records; the source package hash and parent provenance remain in the request |
| GIS edit roundtrip (BK51) | Download the current edit pack, read a bounded edit file, confirm longitude/latitude order, provide a reason, preview revisions, separately confirm effects, then commit | `/api/admin/exchanges/gis/edit-packs`, `/edit-previews`, and `/edit-commits` | Non-allowlisted properties and unreviewed status/access writes |
| Private field visit | Plan, record occurrence, attach an existing observation, and close by explicit action | Existing `/api/visits` and `/api/visits/{id}/observations` revision-bound endpoints | Visit planning is offered only for a site the server marks route-eligible; no geolocation is requested |
| Historical relationships (BK31) | View source-backed typed assertions and uncertainty/date context; add assertions only if the server pilot is enabled | `/api/pilots/status` and `/api/pilots/historical/assertions` | Changes to site trust or access; uncertain assertions remain visually distinct |
| Publication preview (BK32) | Select fields and make explicit selection, rights, and coordinate decisions; build/download a private JSON preview | `/api/pilots/status` and `/api/pilots/publication/preview` | No hosting or publish operation; private starts, questions, observations, route data, and raw imports are not selected by default |
| Local offline notebook | Explicitly approve one server-created pack and persistent device storage; local notes keep original request IDs; check the server revision, queue/review the note, then explicitly click “Lever godkjent observasjon” after `approved_for_sync` | `/api/pilots/offline/packs` and its pack/outbox/review/`{original_request_id}/sync` subroutes | Bearer credentials, tiles, automatic upload/sync, and unrelated catalogue records |

Server pilot flags are authoritative. A disabled pilot remains unavailable in the UI regardless of local form state. A review receipt never triggers delivery: approved observation sync requires its own deliberate button action and sends only the original request ID plus the explicitly checked site revision. The client does not treat a preview or review receipt as publication approval, a safety/access determination, or proof of synchronization.

## Strict input and local storage

Both the main application and the standalone notebook reject ambiguous JSON. The standalone parser validates JSON grammar before parsing, rejects duplicate decoded keys, limits nesting to 64 containers and UTF-8 source to 256 KiB, rejects non-finite numeric results and BOMs, and uses fatal UTF-8 decoding for byte inputs. Offline pack semantics additionally require the exact versioned field set, bounded record count, unique stable site keys, nonnegative integer revisions, and finite in-range coordinates.

IndexedDB contains only allowlisted pack fields (`pack_id`, bounded selected payload, checksum, expiry, site ID/key, and local storage time) and outbox fields (pack/site/revision identifiers, original request ID, and the date/outcome/note payload plus explicitly generated local review state). Unknown fields are rejected before writing; neither writer spreads caller objects. The limits are five local packs, 50 outbox notes, 256 KiB per pack, and 16 KiB per note. The bearer token exists only in the standalone page's memory while an explicit manual request is in progress.

An explicit clear removes the local pack and its local outbox entries. A server-side copy is reported as cleared only after a successful server receipt; offline or failed remote deletion is shown as unconfirmed. An approved sync receipt is reduced to `synced`, original request ID, idempotency flag, observation ID, and resulting site revision; the returned observation/site bodies and authorization token are not persisted. A network failure retains the original ID and leaves the action retryable; a 409 clears the locally checked revision and blocks delivery until another explicit check, while a revision mismatch still requires a new pack and review. No service worker, map-tile cache, background sync, or automatic upload is installed. Clearing browser site data outside the UI remains a device-owner action.

## Verification and acceptance limits

The focused Chromium proof is `tests/test_workflow_browser.py`. It exercises dossier hash binding and sandboxed HTML preview, duplicate-key import rejection and selected-subset commit, revision-bound GIS preview/commit, private visit transitions and observation attachment, explicit local storage and manual review/clear behavior, retry after a simulated committed-but-lost sync response using the same request ID, changed-revision sync blocking, historical/publication pilot gates, and standalone parser/storage canaries. The parent-owned `tests/test_offline_sync_integration.py` exercises the actual local server contract: approval required, observation creation under the original request ID, idempotent replay, one sync event, and current-site revision conflict. Browser/API fixtures use isolated temporary databases and synthetic pilot/exchange data; the authenticated detail page uses the repository's bundled sample catalogue record. The browser fixture verifies that `workflow-ui.js` was fetched exactly once through the application shell.

Local browser and backend tests do not establish production configuration, device-specific IndexedDB persistence/clearing, offline field usability, owner authorization of sample data, an independent BK31 assertion review, or publication rights. Those gates remain with the application owner and pilot reviewers. No production/private database or provider was used for this verification.
